# Taste
- Protects existing user data above all: version upgrades must never delete, reset, or silently alter existing records — only additive schema changes (ADD COLUMN + backfill UPDATE), no DROP/DELETE. Confidence: 0.75
- Expects claims about upgrade safety to be proven, not asserted — compare against the previously released version (byte-diff the old migrations, same bundle identifier / DB path / dependency versions) and actually rehearse the upgrade against a database built from real old data before saying it is safe. Confidence: 0.7
- Old records must remain *visible* in the new version, not merely present in the database — check the load/filter/upkeep path for anything that would hide or close them on first launch. Confidence: 0.6
- Prefers minimal, non-invasive changes: if nothing is actually broken, leave the code alone; only repair real breakage rather than refactoring or "improving" working behavior. Confidence: 0.7
- When temporary verification scripts/databases are created, they should live outside or be cleaned up from the repo working tree afterwards. Confidence: 0.5
- Reports problems by pasting raw build/tool/CI output verbatim or narrating what happened in plain, unedited language (e.g. "I installed it on my MacBook and the buttons are gone, then a pop-up said the update wasn't available") with little or no instruction attached, expecting the agent to diagnose the underlying cause rather than ask for repro steps. Confidence: 0.65
- Judges a release by doing a real end-user install of the published artifact, and treats unsigned/unnotarized installers (Gatekeeper "may contain malware"), broken in-app update checks, and missing platform-native chrome as genuine defects to fix, not as user error. Confidence: 0.65
- Build/bundle-size warnings should be fixed at the root (trim or lazy-load the offending dependency) rather than silenced by raising the configured budget threshold. Confidence: 0.5
- Every change ships with a version bump *and* a changelog entry written in the changelog itself, covering all the changes made in that pass — not just the headline one. Confidence: 0.7
- A version number must be identical in *every* place that spells it out ("make version as 3.0.1 very where[r]"): package.json, lockfiles, Cargo.toml/Cargo.lock, tauri.conf.json, app constants, README/SETUP/docs — treat one stale string anywhere as a defect and verify the agreement afterwards, and keep the changelog consistent too (no heading for a version that was never released, no duplicate release sections — fold an uncommitted entry into the section that is actually being shipped). Confidence: 0.7
- Visual/layout reports ("there's too much gap below the title bar") must be confirmed on screen, not argued from code: render the app, measure the actual box offsets, and answer the "do you really see this, or am I the only one?" question honestly with the numbers behind it. Confidence: 0.55
- Primary actions of a dialog/panel must stay visible without scrolling: reports it as a defect when a popup grows so tall that "Cancel"/"Done" fall below the window edge, and wants the height kept short so both buttons are on screen. The fix expected is structural — cap the card to the available window height, scroll only the middle content, and pin the action row in a fixed footer — not just trimming copy. Confidence: 0.7
- UI control labels must state literally what the press does, and each control means exactly one thing: rejects labels that blur into each other (a "Pause" next to a "Hold on") and rejects one button silently doing two actions (a "Next" that also skips the queued item). Confidence: 0.6
- Wants meaningful events announced at the OS/system-notification level, not only inside the app window. Confidence: 0.5
- Dismiss/close controls on in-app cards belong in the top-right corner of the card itself — states the convention as the rule ("usually the cross button has a pattern to appear at the top right side") and explicitly scopes it to in-app toasts rather than system-level notifications. Confidence: 0.65
- Expects a labeled action to finish the whole job it names in a single press: "Skip Current Task" must skip *and* start the next session automatically, not leave it queued for a separate Start — leaving the rest to a second button press is reported as a bug. Confidence: 0.65
- Wants tight, uniform shell gutters: complains that large spacing tokens leave "big empty space around main tag" and asks for one small inset (~20px on all four sides) shared by the main content area *and* the sidebar, rather than asymmetric xl/2xl padding on each region. Repeats the number as a hard spec rather than a suggestion ("let's make it a 20-pixel … left, right, or bottom, make it 20 pixels"), so treat the gutter as an exact value to apply everywhere, including regions that were previously slightly smaller. Confidence: 0.75
- Expects the layout to hold at every size — phone, tablet, desktop, large monitor — with the gutter staying the *same* across breakpoints ("that must not break, that must remain same"); extra breathing room on big screens should come from capping the content column, not from growing the padding. Confidence: 0.6
- Says so plainly when a summary or doc sentence uses jargon they don't follow ("i do not understabnd it") and wants it unpacked: define each term, restate the whole thing in one plain sentence, then the concrete step-by-step that follows from it — not a louder repetition of the same wording. Confidence: 0.5
- Hands over a working reference implementation (another site/app of theirs) as the spec for look and feel, but insists it be used as reference only — "take a reference, not a copy paste" — so the structure, flow and presentation are matched while the code is written fresh for the target project. Confidence: 0.75
- When the app already has the entry point for a feature (an existing card and "Details" button), the new behavior is wired behind that existing UI; rejects the feature being dropped in somewhere else or a second parallel component being added ("do not put the counter anywhere … map list there only"). Confidence: 0.7
- Expects finished, runnable, verified code rather than a plan, outline or snippet ("give me a working code"). Confidence: 0.55
- Offers to supply the inputs the agent is missing — site URLs, secret keys, API keys — and would rather be asked for a credential than have one guessed or the feature left half-wired. Confidence: 0.5
- Distinguishes the web app from the native/desktop build and scopes a feature to the web app when that is what was asked ("we stick to just for web app"), even if the same view frame also exists in native. Confidence: 0.45
- Settings for a feature belong in the one central Settings page ("all the settings should remain in a settings routing that we already have, that's a central location"), while the Dashboard gets a one-click quick toggle over the same preference — turning something on or off must never cost five or six clicks, and the quick control must be linked to the same stored value rather than a parallel copy. Confidence: 0.75
- Reminders must be both in-app and system-level, and stay put until the user manually interacts with them: keeps re-alerting/re-posting ("keep pressing the bell … until he does not interact") and only closes on an explicit answer, not on a timeout. Confidence: 0.7
- A pause/quiet mode means *nothing at all* gets through, on every path: no sound, no in-app card/toast, no OS notification, no repeat or re-post loop — a session that completes while paused, a task-completed announcement, and an alert already ringing when Pause is pressed are all included. Partial pausing is a bug report ("Rest of other things are paused … That is the main purpose of having things paused"), so treat any user-facing output channel as in scope and gate it on the pause flag rather than fixing just the one path that was noticed. Confidence: 0.75
- Briefs a feature roughly and expects the agent to fill in the design decisions itself — the menu/section name, the card copy, the wording — while stating its own logic ("I am giving you a rough idea … think yourself as well and give your logics"); asks to be judged on whether it makes a normal user's life better. Confidence: 0.6
- A feature's settings card and dashboard surface should carry a short plain-language "why it helps" line explaining the benefit, not just the controls. Confidence: 0.5
- Insists on a hard day boundary: a new day must start completely fresh — session count, cycle/break type, linked task, water and stand-and-walk cadence, and the congratulation/completion popup — with no reference carried over from yesterday, and nothing at all firing the instant the app opens. Reports the symptom as a concrete scenario ("two sessions yesterday, one remaining today, and completing it congratulated yesterday's cycle") and then asks for *all* the stale references removed ("remove all those … a first-day fresh start for everything"), so treat the whole class of carried-over state as the defect, not only the one path that was noticed. Confidence: 0.75
- Wants first-run onboarding to be a single one-time setup popup where a fresh install opts into the optional behaviors (pin as startup, always-on-top, tray, and the body reminders), and adding controls there must be purely additive — the existing Dashboard equivalents stay exactly as they are ("although on the dashboard, we already have it, keep it as it is"). Confidence: 0.6
- A preference switched off in one place must be off everywhere: no card, no tone, no system notification from any other surface (onboarding, dashboard, settings, desktop) — "if the user marks it as off, it should be off throughout". Confidence: 0.65
- Names the target version at the start of the task and scopes the whole pass to it: bring everything to that version if it is not already there, leave it alone if it is, and keep all subsequent work shipping under that one version rather than rolling it further ("whatever we discuss, keep it under that only"). Confidence: 0.55
- Judges optional features against the app's core purpose: anything that generates pop-ups, bells or repeated reminders is "noise" and an obstacle to the deep-work theme, so such features must ship *available but off by default* rather than enabled for everyone — "we will keep them as a feature, but we will keep them off by default". Confidence: 0.75
- A capability that is off by default must still be discoverable without being imposed: the app periodically *offers* it (a prompt in-app and at system level, with one click to set it up and one click to "stop asking"), always says the user can opt out any time in a single click, and never turns anything on unasked. Confidence: 0.7
- After applying defaults on the user's behalf, spells out exactly what is now in force — the working window ("time from this to this"), the reminder interval, the amount per event — so the user is never guessing what configuration they just accepted. Confidence: 0.6
- Form placeholder text must be generic and belong to nobody: explicitly forbids placeholders that match a real person's name, mobile number or email ("do not match anybody in terms of mobile number, name, or email") — use neutral examples like "Your full name", "you@example.com", "+00 00000 00000". Confidence: 0.6
- A contact/reach-the-owner surface should offer several channels, not only a form ("he can mail me on this, or … there can be a number of other options"): a short form (name required, email and mobile optional) plus the direct email and the existing social/profile links. Confidence: 0.5
- Picks realistic everyday defaults over the most conservative/smallest option ("we have 30 ml as a default … make it 50 ml"), i.e. the value a normal user would actually choose, not the timid minimum. Confidence: 0.45
- Their own private contact details must never appear in the shipped product: a personal mobile number is a defect anywhere it surfaces ("we are showing my mobile number … remove it. This mobile number from everywhere"), and "from everywhere" means every path it leaked into — contact-channel constants and their links, the about/contact page copy and icons, the privacy/terms text, and the specs that assert those labels — not just the one screen that was noticed, with nothing left behind for a later grep to find. Confidence: 0.65
- Treats search-engine and AI-agent discoverability as a baseline expectation for every published site he ships — robots.txt that names and allows search plus LLM crawlers, sitemap.xml, llms.txt, canonical/Open Graph/Twitter metadata and JSON-LD — and raises it as a class-level defect ("these websites are not agent or search engine friendly … and related many others"), not a per-site one-off. Confidence: 0.5
- Navigation highlighting must hold while traversing a section: a page that is opened *from* a nav item (Contact and the privacy/terms policies under About) keeps that parent item lit, so the nav never goes dark mid-journey ("always keep highlighting when I'm traversing these pieces … keep it highlighted in the same way"); the styling/active rule itself stays unchanged, and exactly one item is highlighted at a time. Confidence: 0.7

# Taste
- Protects existing user data above all: version upgrades must never delete, reset, or silently alter existing records — only additive schema changes (ADD COLUMN + backfill UPDATE), no DROP/DELETE. Confidence: 0.75
- Expects claims about upgrade safety to be proven, not asserted — compare against the previously released version (byte-diff the old migrations, same bundle identifier / DB path / dependency versions) and actually rehearse the upgrade against a database built from real old data before saying it is safe. Confidence: 0.7
- Old records must remain *visible* in the new version, not merely present in the database — check the load/filter/upkeep path for anything that would hide or close them on first launch. Confidence: 0.6
- Prefers minimal, non-invasive changes: if nothing is actually broken, leave the code alone; only repair real breakage rather than refactoring or "improving" working behavior. Confidence: 0.7
- When temporary verification scripts/databases are created, they should live outside or be cleaned up from the repo working tree afterwards. Confidence: 0.5
- Reports problems by pasting raw build/tool/CI output verbatim or narrating what happened in plain, unedited language (e.g. "I installed it on my MacBook and the buttons are gone, then a pop-up said the update wasn't available") with little or no instruction attached, expecting the agent to diagnose the underlying cause rather than ask for repro steps. Confidence: 0.65
- Judges a release by doing a real end-user install of the published artifact, and treats unsigned/unnotarized installers (Gatekeeper "may contain malware"), broken in-app update checks, and missing platform-native chrome as genuine defects to fix, not as user error. Confidence: 0.65
- Build/bundle-size warnings should be fixed at the root (trim or lazy-load the offending dependency) rather than silenced by raising the configured budget threshold. Confidence: 0.5
- Every change ships with a version bump *and* a changelog entry written in the changelog itself, covering all the changes made in that pass — not just the headline one. Confidence: 0.7
- Visual/layout reports ("there's too much gap below the title bar") must be confirmed on screen, not argued from code: render the app, measure the actual box offsets, and answer the "do you really see this, or am I the only one?" question honestly with the numbers behind it. Confidence: 0.55
- UI control labels must state literally what the press does, and each control means exactly one thing: rejects labels that blur into each other (a "Pause" next to a "Hold on") and rejects one button silently doing two actions (a "Next" that also skips the queued item). Confidence: 0.6
- Wants meaningful events announced at the OS/system-notification level, not only inside the app window. Confidence: 0.5
- Wants tight, uniform shell gutters: complains that large spacing tokens leave "big empty space around main tag" and asks for one small inset (~20px on all four sides) shared by the main content area *and* the sidebar, rather than asymmetric xl/2xl padding on each region. Repeats the number as a hard spec rather than a suggestion ("let's make it a 20-pixel … left, right, or bottom, make it 20 pixels"), so treat the gutter as an exact value to apply everywhere, including regions that were previously slightly smaller. Confidence: 0.75
- Expects the layout to hold at every size — phone, tablet, desktop, large monitor — with the gutter staying the *same* across breakpoints ("that must not break, that must remain same"); extra breathing room on big screens should come from capping the content column, not from growing the padding. Confidence: 0.6
- Says so plainly when a summary or doc sentence uses jargon they don't follow ("i do not understabnd it") and wants it unpacked: define each term, restate the whole thing in one plain sentence, then the concrete step-by-step that follows from it — not a louder repetition of the same wording. Confidence: 0.5
- Hands over a working reference implementation (another site/app of theirs) as the spec for look and feel, but insists it be used as reference only — "take a reference, not a copy paste" — so the structure, flow and presentation are matched while the code is written fresh for the target project. Confidence: 0.75
- When the app already has the entry point for a feature (an existing card and "Details" button), the new behavior is wired behind that existing UI; rejects the feature being dropped in somewhere else or a second parallel component being added ("do not put the counter anywhere … map list there only"). Confidence: 0.7
- Expects finished, runnable, verified code rather than a plan, outline or snippet ("give me a working code"). Confidence: 0.55
- Offers to supply the inputs the agent is missing — site URLs, secret keys, API keys — and would rather be asked for a credential than have one guessed or the feature left half-wired. Confidence: 0.5
- Distinguishes the web app from the native/desktop build and scopes a feature to the web app when that is what was asked ("we stick to just for web app"), even if the same view frame also exists in native. Confidence: 0.45
